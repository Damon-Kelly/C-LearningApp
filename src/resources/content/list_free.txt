# Linked lists: memory leaks and freeing a whole list.
# Code outputs are checked by running:  python3 tools/verify_content.py

@topic Freeing a list
@summary Memory leaks, deleting every node, and the use-after-delete trap

#---------------------------------------------------------------------------
@page explain Every new needs a delete
@text
Each node was created with new, so each one must be deleted exactly once. Memory you forget to delete is a memory leak: it stays reserved until the program ends and cannot be reused. A program that leaks in a loop can eventually run out of memory.
@end
@text
Lists leak easily. If you only delete the head node, the rest of the nodes are still on the heap, but nothing points at them any more. The same happens if you simply assign headPtr = nullptr: the pointer is cleared, but the nodes are not given back.
@end
@code cpp
struct Node { int data; Node* nextPtr; };

int main() {
    Node* headPtr = new Node{1, new Node{2, nullptr}};
    // WRONG: only the first node is freed, the second one leaks
    delete headPtr;
    headPtr = nullptr;
    return 0;
}
@end
@text
Freeing a list means visiting every node and deleting each one.
@end

#---------------------------------------------------------------------------
@page explain Deleting every node
@text
Walk the list as usual, but before deleting a node, step the walker forward. After the delete the node's memory is gone, so you can no longer read its nextPtr.
@end
@code cpp
struct Node {
    int data;
    Node* nextPtr;
};

void FreeList(Node** ptrToHeadPtr) {
    Node* curNodePtr = *ptrToHeadPtr;
    while (curNodePtr != nullptr) {
        Node* tempPtr = curNodePtr;
        curNodePtr = curNodePtr->nextPtr;
        delete tempPtr;
    }
    *ptrToHeadPtr = nullptr;
}

int main() {
    Node* headPtr = new Node{1, new Node{2, new Node{3, nullptr}}};
    FreeList(&headPtr);
    cout << (headPtr == nullptr) << endl;
    return 0;
}
@output
1
@end
@text
tempPtr remembers the node to delete while curNodePtr moves ahead. At the end *ptrToHeadPtr is set to nullptr so the caller's head does not keep pointing at memory that no longer exists. That is why the function takes Node**.
@end

#---------------------------------------------------------------------------
@page explain The classic mistake
@text
The tempting version deletes the node and then reads from it. It compiles, and it may even seem to work, but it uses memory that has been given back, which is undefined behaviour.
@end
@code cpp
struct Node { int data; Node* nextPtr; };

void BadFree(Node* headPtr) {
    Node* curNodePtr = headPtr;
    while (curNodePtr != nullptr) {
        delete curNodePtr;
        curNodePtr = curNodePtr->nextPtr;   // BUG: curNodePtr was just deleted
    }
}

int main() { return 0; }
@end
@text
After delete curNodePtr, the node no longer belongs to you, yet the next line reads its nextPtr. Always save the next pointer before the delete, as FreeList does.
@end
@text
Related rules: never delete the same node twice, never use a pointer after deleting what it points at, and set a pointer to nullptr after freeing when it will live on. Tools such as Valgrind or the compiler's address sanitiser find these problems automatically.
@end

@page predict Predict the output
@text
What does this program print?
@end
@code cpp
struct Node { int data; Node* nextPtr; };
Node* h = new Node{1, new Node{2, new Node{3}}};
int freed = 0;
while (h != nullptr) {
    Node* t = h; h = h->nextPtr;
    delete t; freed++;
}
cout << freed << " " << (h == nullptr) << endl;
@output
3 1
@end
@option 3 0
@option 2 1
@option 0 1
@option 3 1
@answer 4
@why The loop deletes one node per pass, so 3 passes make freed equal 3. It only stops when headPtr is nullptr, so the second value is 1 (true).

@opt delete is slow
@opt After delete the node's memory is invalid, so its nextPtr cannot be read
@opt The next pointer is cleared by the compiler
@opt To avoid compile errors
@correct 2
@why Reading from a deleted node is undefined behaviour.

@q Why does FreeList set *ptrToHeadPtr = nullptr at the end?
@opt So the caller's head does not point at freed memory
@opt To save memory
@opt To delete the last node
@opt It is required by new
@correct 1
@why Otherwise the caller's head would be a dangling pointer to a deleted node.

@q Which of these is a mistake?
@opt Deleting every node exactly once
